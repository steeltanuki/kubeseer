# Kubeseer v0.1.3

## Highlights

- The release workflow now fetches the version tag and protected `main` history in its publication job, so the job can independently verify the same source commit that passed its gates before publishing the controller image, Helm OCI chart, and GitHub Release.
- The E2E readiness gate waits for its port-forward before checking `/readyz`, preserving the Kubernetes certification that precedes publication.
- This patch changes release automation and version metadata; it does not change the Kubeseer API, controller behavior, or chart values schema.

## Upgrade considerations

- Use the `0.1.3` Helm OCI chart with the matching `ghcr.io/steeltanuki/kubeseer:0.1.3` controller image. The certified target remains Linux/amd64, Kubernetes 1.35.6 and 1.36.2, and Helm 3.12 or newer.
- The earlier `v0.1.0`, `v0.1.1`, and `v0.1.2` release attempts did not complete publication. Those tags remain historical records and are not retargeted. Select a version only after its GitHub Release and public image and chart are present.
- Before upgrading an existing installation, run the documented CRD compatibility check and apply compatible CRDs with an explicit kubeconfig and context. Preserve the installation access policy, observed-resource RBAC, and certificate settings across the upgrade or rollback.
- The default certificate mode requires cert-manager. The `externalSecret` mode requires an administrator-managed serving Secret and public CA bundle. A normal Helm uninstall retains the CRDs, Kubeseer resources, and installation access policy.
