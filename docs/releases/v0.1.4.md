# Kubeseer v0.1.4

## Highlights

- The release publisher now checks GHCR with the workflow's package credentials before deciding whether a versioned image or Helm chart is absent. GHCR can return HTTP 403 to an anonymous token request for a package that has never been created; that response no longer blocks the first push.
- Existing artifacts still need an anonymous pull with the expected digest before they can be reused. After a push, the publisher verifies public access before continuing to the next artifact or creating the GitHub Release.
- This patch changes release automation and version metadata. The Kubeseer API, controller behavior, chart values schema, and supported platform are unchanged.

## Upgrade considerations

- Install the `0.1.4` Helm OCI chart with the matching `ghcr.io/steeltanuki/kubeseer:0.1.4` image after the GitHub Release and both public GHCR packages are available. The certified target remains Linux/amd64, Kubernetes 1.35.6 and 1.36.2, and Helm 3.12 or newer.
- GHCR makes a newly created package private by default. On the first publication, the workflow may stop after pushing the image or chart. The maintainer must make each new package public and rerun the same protected `v0.1.4` workflow; the publisher reuses matching immutable artifacts and creates the GitHub Release only after both are publicly retrievable.
- The `v0.1.0` through `v0.1.3` attempts did not complete publication. Keep those tags unchanged and select a version only after its GitHub Release and public image and chart are present.
- Before upgrading an existing installation, run the documented CRD compatibility check and apply compatible CRDs with an explicit kubeconfig and context. Preserve the installation access policy, observed-resource RBAC, and certificate settings across upgrade or rollback. The default certificate mode needs cert-manager; `externalSecret` needs an administrator-managed serving Secret and public CA bundle. A normal Helm uninstall retains CRDs, Kubeseer resources, and installation access policy.
